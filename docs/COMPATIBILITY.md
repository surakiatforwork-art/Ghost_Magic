# Ghost Magic Android capability migration

Research date: 2026-10-16. This is an implementation contract and migration backlog, not a claim that these capabilities are already implemented or tested. Android OS version, target SDK, device manufacturer, granted permissions and execution context all affect availability. Test the actual combination before declaring support.

## Capability classes

- **Native**: a documented public API available to an ordinary app, sometimes after a user grant.
- **User assisted**: open a system dialog/panel; the user performs or confirms the change. Opening it is not proof the requested setting changed.
- **Privileged future**: a separately designed, explicitly activated root/ADB/device-owner/system bridge. This is not part of the first milestone. A bridge does not automatically acquire every permission, and its supported commands need individual validation.
- **Unsupported**: cannot be promised for an ordinary app in that environment. Never silently report success or substitute a different action.

## Migration matrix

| Capability | Modern Android constraint and chosen migration | Initial scope / later work | Required verification |
| --- | --- | --- | --- |
| Post a notification | **Native**. Create a channel on API 26+. Android 13+ requires `POST_NOTIFICATIONS` for ordinary notifications; users can also disable channels. [Permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission), [channels](https://developer.android.com/develop/ui/views/notifications/channels). | First milestone: permission preflight and clear denied result. Posting a notification is distinct from listening to other apps' notifications. | Grant, deny, revoke and disabled-channel cases; tap behavior; no false success when blocked. |
| Change system brightness | **Native after special access**: declare `WRITE_SETTINGS`, check `Settings.System.canWrite()`, offer `ACTION_MANAGE_WRITE_SETTINGS`. Write bounded system brightness only when manual mode is already selected; reject adaptive mode rather than silently changing that preference. App-window brightness is a different action. [API contract](https://developer.android.com/reference/android/provider/Settings.System). | First milestone: explicit permission workflow and system brightness action. Do not claim hardware luminance precision; adaptive brightness and OEM behavior vary. | No access, access revoked, automatic/manual mode, minimum/maximum, read-back and visible effect on a device. |
| Toggle Wi-Fi | Ordinary apps targeting API 29+ cannot use `setWifiEnabled()` to toggle Wi-Fi. **User assisted**: API 29+ Internet/Wi-Fi settings panel; settings screen fallback. Direct toggle is **unsupported** for the standard app; managed/system exceptions and a **privileged future** adapter are separate. [WifiManager](https://developer.android.com/reference/android/net/wifi/WifiManager), [panel](https://developer.android.com/reference/android/provider/Settings.Panel). | First milestone action is named **Open Wi-Fi panel**, with a user-action-required trace. It is not an automated toggle. | Panel resolves, cancel/return, no state-change success claim; OEM panel behavior. |
| Toggle Bluetooth | For apps targeting API 33+, `enable()`/`disable()` fail for ordinary apps. **User assisted** enabling through `ACTION_REQUEST_ENABLE`; settings for disabling. Runtime Bluetooth permissions depend on operation and OS. Direct toggle is **unsupported**, with managed/system exceptions assessed separately. [Android 13 change](https://developer.android.com/about/versions/13/behavior-changes-13), [setup](https://developer.android.com/develop/connectivity/bluetooth/setup). | Later capability adapter. **Privileged future** remains a research item, not a promised workaround. | Permission denial, unsupported hardware, canceled dialog and actual resulting adapter state. |
| Toggle mobile data | Public setter requires privileged `MODIFY_PHONE_STATE` or carrier privileges. An ordinary runtime permission dialog cannot grant that authority. **User assisted** Internet/mobile network settings; direct toggle **unsupported** in standard mode. [TelephonyManager](https://developer.android.com/reference/android/telephony/TelephonyManager#setDataEnabledForReason(int,%20boolean)). | Later settings action. Optional **privileged future** investigation must account for subscriptions, OEM behavior and unavailable telephony hardware. | Dual SIM/default-data subscription, no SIM, cancel and state confirmation. |
| Exact-time trigger | **Native with eligibility/access checks**: prefer inexact scheduling when timing permits. Exact alarms on modern targets may require special access; on Android 14 it is denied by default for most new installs targeting 33+. Check `canScheduleExactAlarms()` and offer the system access page only when needed. Do not use `USE_EXACT_ALARM` merely to avoid this grant. [Alarm guide](https://developer.android.com/develop/background-work/services/alarms). | Later trigger milestone. Permission refusal must produce an explicit disabled trigger or an explicitly selected inexact alternative. | Deny/revoke, Doze, reboot/reschedule, clock/time-zone changes and daylight saving transitions. |
| Deferred/background work | **Native but scheduled**: ordinary JobScheduler in 0.2; WorkManager remains an option for future richer work dependencies. Periodic work has a 15-minute minimum interval and is subject to constraints/OS scheduling. [JobScheduler](https://developer.android.com/reference/android/app/job/JobScheduler), [work requests](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work). | 0.2 adds persisted periodic jobs, revision/generation admission, journal, interruption detection, stop controls and duplicate-window suppression. See [runtime contract](BACKGROUND_RUNTIME.md). Node-level resume and broader background/event policies remain future work. | Process death, duplicate delivery, force-stop behavior, natural intervals, Doze and OEM restrictions. |
| Foreground service | **Native within rules**, not an unrestricted permanent engine. API 31+ restricts background starts; API 34+ requires appropriate service type and permissions. Android 15/16 add further service/job limitations. Select a legitimate type per workload instead of labeling all automation `dataSync`. [Start rules](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), [types](https://developer.android.com/about/versions/14/changes/fgs-types-required), [15](https://developer.android.com/about/versions/15/behavior-changes-15), [16](https://developer.android.com/about/versions/16/behavior-changes-16). | Later workload-by-workload design. Arbitrary invisible indefinite execution is **unsupported** as a blanket promise. | Start from UI and background, stop notification, timeout, reboot, permission loss and service-type compliance. |
| Accessibility/UI actions | **Native service after explicit system enablement**; configure only needed event/window/gesture capabilities. Accessibility is not a generic grant to restricted system APIs, and UI selectors can break across app/OEM updates. [Service guide](https://developer.android.com/guide/topics/ui/accessibility/service). | Later separate, visible opt-in module. No accessibility service in the initial core milestone. Before distribution, review applicable store policy for the actual use case. | Service disabled/revoked, screen locked, absent nodes, secure windows, interruption and cancellation. |
| Flow file import/export and file actions | **Native** app-private persistence; **user assisted** Storage Access Framework for selected documents using `ACTION_OPEN_DOCUMENT`/`ACTION_CREATE_DOCUMENT`. Persist URI access only when offered and needed; a URI can disappear or lose access. Do not port arbitrary legacy filesystem paths unchanged. [Document access](https://developer.android.com/training/data-storage/shared/documents-files), [scoped storage](https://developer.android.com/training/data-storage). | First milestone: versioned Ghost Magic JSON import/export through picker. Legacy XML and arbitrary filesystem actions are later migrations. | Round trip, malformed/oversized input, unknown schema, revoked URI, provider errors, canceled picker, no partial overwrite. |

## Runtime and migration rules

Each node needs a capability preflight and a trace result that distinguishes completed, failed, canceled, unsupported and user action required. A permission prompt must not silently advance the graph as though the action happened. Do not automatically resume a side effect after returning from settings without rechecking permission/state and the intended run.

Legacy imports must retain original node identity/type/configuration in a migration report. Unknown nodes stay visibly unsupported; never drop them and call the flow converted. Native replacement, user-assisted replacement and privileged-only replacement are different migration outcomes. Validate all nodes before enabling a migrated flow.

The first Android device test set should include API 29, 31, 33, 34, 35 and 36; add every newer stable release and at least one OEM device before a broad compatibility claim. These are proposed test gates, not a tested-device list. Build success or APK installation alone does not prove action behavior or background reliability.
